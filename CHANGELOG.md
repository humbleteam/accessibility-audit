# Changelog

## [1.12.0] - 2026-10-29

- The scope line was the one of the four homes with no SC numbers in it. A finding carries its `WCAG 2.2 SC x.x.x` citation, and the Output format template gives the ledger and the suppressed roster `<SC number and name>` each, while the scope line read `<one line on what was actually checked>` - so the home that holds the checked-and-clean criteria was the only one a reader could not count, which makes it the only one a criterion can disappear from without leaving a visible gap. The 18-criteria accounting rule has been this repo's spine since 1.0.0 and it was never checkable end to end.
- Prose is also ambiguous in the one way that matters here. "Contrast, target size and visible labels were checked" names what was examined, and examining a criterion is how a finding starts, so that list cannot tell a reader which of the three came back clean and which are written up below. The screenshot report in the README was exactly this shape: a five-item prose list of what was read, two of whose items - visible labels and heading and label text - are the P1 and the P2 underneath it.
- The rule now reads: conditions and coverage in prose, then `Checked and clean: <number> <short name>`, comma-separated. Stated in Output format, in Step 3 where the four homes are defined, and in the README's accounting bullet, so all three agree.
- The screenshot example's scope line carries it - `Checked and clean: 1.4.11 non-text contrast, 2.5.8 target size` - and both multi-screen templates do too, since the scope line is per screen. The JSX example already named its clean six by number and is unchanged; the divergence between the two examples is what surfaced the gap.
- A criterion whose working is not reproducible from the report still names the control or pair it turned on. That was already true of the 2.5.8 exemption and is now stated as the rule behind it: the scope line is where such a verdict is final, with no finding underneath it to carry the evidence.
- No criterion moved and no count moved. The screenshot report still reconciles at 2 clean, 3 findings and a 13-criterion ledger, and the JSX report at 6, 4 and 8.

## [1.11.0] - 2026-10-24

- The circle test added in 1.10.0 had no worked instance. SC 2.5.8's spacing exception is a measurement - center a 24 CSS px diameter circle on an undersized target's bounding box and look for an intersection - and the README's screenshot report asserted its result without showing any of it: the scope line said target size "was checked and came back clean" and nothing in the repo rendered the check that produced that verdict.
- A measurement nobody can re-run is a verdict a reader has to take on trust, and this one decides whether a finding exists at all. 1.10.0's own release note is what makes the gap matter: the whole point of that change was that the size is where the check starts rather than where it ends, so the example that models the output was still modelling the behaviour the rule replaced, from the reader's side, by showing a clean 2.5.8 with no working.
- The same example also asserted a 2.5.8 verdict without ever settling the scale. The skill's unknown-scale case says target size goes to the ledger until the device pixel ratio or the CSS viewport width is known, because the criterion is defined in CSS pixels and an image stores device ones, so a report claiming the criterion on the scope line with no scale stated is claiming a reading its own rules put out of reach.
- The screenshot example now carries the measurement end to end. Its scope line states the scale - 390 CSS px, from a 1170 px wide file at a supplied 3x ratio - and names the exempt control, and a new paragraph after the report walks the arithmetic: a 60 x 60 px help control beside the CVC field is 20 x 20 CSS px, the circle's radius of 12 against a box reaching 10 puts its edge 2 CSS px outside the box, and the nearest other target is 9 CSS px clear, so nothing intersects and the spacing condition exempts it.
- It carries the failing case too, because the exemption is only legible against it: the same 20 x 20 control in a row of icons 4 px apart has each circle reaching the next one's, and the identical measurement then files a P1. That is the pair the size alone cannot tell apart, which is the sentence the rule has had since 1.10.0 and now has an instance of.
- No rule moved. The five exceptions, the 5 + 7 + 6 = 18 arithmetic, the four homes, the severity tiers and every criterion's screenshot grade are untouched; 2.5.8 keeps its place on the scope line rather than in the ledger, and this release only shows why it belongs there on that screen.

## [1.10.0] - 2026-10-19

- 2.5.8 was written as a bare measurement. Step 3 said to measure tappable elements "against the 24x24 CSS px minimum", Step 4 listed "a target below the 24x24 CSS px minimum" as a P1, and nothing anywhere said what the criterion says next. SC 2.5.8 states that minimum with five exceptions, so a target under 24x24 is where the check starts rather than where it ends, and an audit reading only the size files a P1 on every small control it meets.
- The direction this fails in is the one the rest of the skill is not built to catch. Every other rule here exists to stop a false pass, and this is its mirror: a finding the criterion does not have, cited to a success criterion that exempts it. It costs more than a wasted line, because the fix a reader applies is to grow the target, and the two exceptions an image can settle are the ones that most often make growing it unnecessary.
- `references/wcag22-checklist.md` already carried the shape of this in its 2.5.8 row - "or have enough spacing to avoid accidental taps" - and that is the whole of what it said. No threshold, no test, no way to tell an exempt target from a failing one, so the hint could not be acted on and the row read as a courtesy rather than a rule.
- New edge case, "A tappable target measuring under 24x24 CSS px", giving the two exceptions a screenshot settles. Spacing is a measurement: center a 24 CSS px diameter circle on the bounding box of each undersized target, and the target is exempt when its circle intersects no other target and no other undersized target's circle. A 20x20 icon button alone in a corner is exempt and the same button 4px from its neighbors in a toolbar is not, which is the pair the size alone cannot tell apart. Inline is the second: a target in a sentence, or sized by the line-height of the non-target text around it, is exempt, and that covers most links in body copy.
- The other three exceptions are named and kept out of the image's reach. Equivalent asks whether a conforming control elsewhere on the page offers the same function, user agent control asks whether the author styled the control at all, and essential is a claim about what the presentation has to convey. None is readable from a static image, so they constrain what a finding says rather than whether one is filed: an undersized target whose circles intersect is a finding, and the finding names those three as the ways the team closes it without measuring again.
- 2.5.8 keeps its screenshot-checkable `Yes` grade, and this is the part that had to be checked rather than assumed. The image carries what decides the ordinary case - the size, the clear space, whether the target sits in a line of text - so the criterion is still reachable from a screenshot and a target an exception clears was checked and came back clean. It goes on the scope line, never in the ledger, which claims the input could not reach it. The 5 + 7 + 6 = 18 arithmetic in Step 3 and in the checklist's reading notes is untouched, and so are the four homes, the severity tiers and every other criterion's grade.
- Step 3's 2.5.8 bullet now says the measurement opens the question, Step 4's P1 example reads "that no exception clears", the checklist row carries the circle test and the inline case, and a new reading note says why the grade did not move. README: the screenshot answer names the spacing check, and a new FAQ answer, "Is a tap target smaller than 24x24 px always a WCAG failure?", carries the two visible exceptions and the three that are not.

## [1.9.0] - 2026-10-14

- The `Example output` preamble called the JSX run's ledger "the eight that need a computed value or a rendered page". Seven of those eight need one; the eighth is 3.3.8, and it is in the ledger because the component holds no sign-in step. The arithmetic was right and the reason was wrong: ten off the code plus eight in the ledger is 18, and a reader who checks the claim instead of the sum finds seven style-dependent and rendered-condition criteria against a stated eight.
- Both other surfaces that state the length already said it correctly, which is what made this one wrong rather than merely loose. Step 3 writes the styleless-markup ledger as "at least the seven style-dependent criteria from Step 3 ... plus any criterion the snippet's scope cannot reach, such as 3.3.8 on a component that holds no sign-in step", the `How it works` bullet says "at least the seven", and `references/wcag22-checklist.md` sorts the same seven across its two reading notes. The preamble was the only place the open-ended length was written as a closed number.
- That is the part a reader acts on. "At least seven" says a styleless-markup ledger has a floor and that the snippet's own scope decides the rest, so a ledger of eight or nine is expected and a ledger of six is a dropped criterion. "Eight that need a computed value or a rendered page" says the length is fixed at eight and names a cause that cannot produce it, so the next audit either files a scope-bound criterion as style-dependent or pads the ledger to reach eight. Both are the silent pass Step 3 exists to prevent, arriving through the count instead of through a criterion.
- The preamble now names the split - seven for the computed value or the rendered page, the eighth for a scope the component does not reach - and the `JSX input` section carries the same split where it introduces its own ledger, with the four computed-value and three rendered-condition criteria told apart and 3.3.8 named as the criterion that would be in the ledger with every style in hand.
- No rule, criterion, severity or ledger entry changed. The example's own ledger already gave 3.3.8 its scope reason on its own line, and the counts were verified unchanged: four findings plus six on the scope line plus eight in the ledger is 18, and the seven style-dependent criteria are 1.4.3, 1.4.11, 2.4.7 and 2.5.8 for a computed value and 1.4.4, 1.4.10 and 2.4.11 for a rendered condition.

## [1.8.0] - 2026-10-07

- Step 1 called a fetch result "the rendered HTML" and Step 3 said a fetch returns the document and not the rendered page. The same input was two things in one file, and the sentence a reader meets first was the wrong one.
- What that left with no legal answer: a URL for a client-rendered app. The fetch succeeds and returns a mount node with its script tags, so the document holds no headings, no form controls, no label associations and no ARIA. The markup path reads structure off exactly those, and with none of them present every criterion it resolves off the code resolves nothing, while the ledger sits at one of the two URL lengths Step 3 defines. The report then states that structure was read and came back clean, off a document with no structure in it. A sign-in wall and a consent interstitial do the same thing by answering with a different page than the one named.
- This is the false pass 1.5.0 fixed for styleless markup, 1.6.0 fixed for markup plus a screenshot and 1.7.0 fixed for source-only audits, arriving a fourth time through a fetch that worked. It is the most convincing of the four, because the fetch did succeed and the input-type line is accurate.
- New edge case, "A URL whose fetch returned a shell rather than the page". How to spot it is readable off the document: a body with no headings, no form controls and no landmarks for a screen that visibly has them is a shell, and a title or form that does not match the page requested is an interstitial. What follows is one of three moves - ask for the rendered DOM an element inspector copies out, ask for a screenshot, or audit what arrived and name it as the shell, in which case nearly every criterion sits in the ledger because the input in hand is not the screen anyone asked about. "The fetch returned HTTP 200" is not a coverage.
- Step 1's URL bullet now says the source of truth is the document the fetch returned, and points at the ledger length in Step 3 and at the shell case. Step 3's URL paragraph says both of its lengths assume the document carries the screen's markup, which a successful fetch does not guarantee. The Output format ledger-length paragraph adds the third outcome for a URL.
- `references/wcag22-checklist.md`: a reading note that the code grades assume there is code to read, since every row a markup input settles is settled by an attribute, a level, an association or a role. README: the accounting bullet carries the shell, and a new FAQ answer on auditing a single-page app from its URL.

## [1.7.0] - 2026-10-01

- The styles rule treated one phrase as one thing. Step 3 said every criterion needing "a computed value or a rendered page" leaves the ledger once the styles arrive with the markup, and those are two different kinds of evidence: a stylesheet is a computed value and a stylesheet is not a rendered page. The markup path's two ledger lengths followed from that merge, and the shorter one was empty.
- What that left with no legal answer: a component pasted with its CSS module. Every declared color, box dimension and focus style is readable, so the four criteria that need a value really do come out - and 1.4.4, 1.4.10 and 2.4.11 ask what the layout does at 200% text size, at 320px wide, and behind a sticky element while a control holds focus. A media query and a `position: sticky` rule state the intent; whether content clips, overlaps or hides the focused element is the outcome, and source code is the input to layout rather than its output. An empty ledger there reports three rendered results nothing rendered, which is the false pass 1.5.0 fixed for styleless markup and 1.6.0 fixed for markup plus a screenshot.
- Step 3 splits the seven style-dependent criteria into four computed-value criteria, which the stylesheet settles, and three rendered-condition criteria, which no source file settles. The markup path now has three ledger lengths: those three with the styles, those three plus the four plus anything the snippet's scope cannot reach without them, and fewer than three only when a rendered view of the missing condition arrived alongside the code. No source-only audit files an empty ledger.
- The URL path had no stated length at all, and the Output format rule named URL inside the case that writes "None - full markup was available". A fetch returns the document, not the stylesheets it links and not the rendered page, so a URL audit holding HTML alone is the styleless-markup length - its class names point at a file the fetch did not follow, exactly as a pasted snippet's do. It is named as that case now, and the scope line says what the fetch actually returned, because "a URL was supplied" is not a coverage.
- "None - full markup was available" is retired: a source-only audit cannot write it. The one input that empties the ledger is code plus a rendered view of each of the three conditions, and the line then names them, which is what makes the claim checkable.
- 2.4.7 and 2.4.11 are no longer a fixed pair. They travel together only where no stylesheet arrived, since a declared focus style resolves 2.4.7 and nothing declared resolves 2.4.11; the markup-plus-screenshot edge case says so where it lists them side by side.
- `references/wcag22-checklist.md`: the reading notes say which partial rows stay partial on a code audit, and that a `Yes` grade means a static image is enough rather than that markup alone is. README: the accounting bullet carries the three-criterion length and the fetch distinction.

## [1.6.0] - 2026-09-23

- Step 1 asks for two inputs to be used together and Step 3 had no shape for the pair. "If more than one input type is given (for example a URL plus a screenshot of one of its states), use both and check against the wider scope" sends the audit down the markup path carrying an image, and the markup path recognises exactly two ledger lengths: empty when the styles came with the markup, and the seven style-dependent criteria plus whatever the snippet's scope cannot reach when they did not. A screenshot is neither styles nor nothing.
- What that left with no legal answer: a JSX component pasted with a screenshot of the rendered screen. Writing "None - full markup was available" claims a coverage the styles never gave, and it is the false pass this repo already fixed once for styleless markup in 1.5.0. Leaving all seven in the ledger is the opposite error and the newer one, because the ledger says the input could not reach a criterion, and a rendered image of the screen reaches contrast, non-text contrast and target size for everything it shows.
- New edge case, "Markup plus a screenshot of the same screen". The image is the styles for what it renders: 1.4.3 and 1.4.11 leave the ledger for the text pairs, icons and borders actually visible in it, and 2.5.8 leaves once the scale is settled under the unknown-scale case. The remaining four stay unless the matching image was supplied, 1.4.4 at 200% text size, 1.4.10 at 320px wide, 2.4.7 and 2.4.11 in a focus state, which is the partial-criteria test from Step 3 applied inside the markup path rather than a new rule.
- The scope line now names which images arrived, not that a screenshot did. "A screenshot was supplied" and "the focus state was supplied" are different coverages, and only the second one clears 2.4.7.
- Step 3's markup paragraph names the screenshot as the third thing that moves a criterion out of the ledger, alongside a resolvable inline color and a stated computed value, scoped to what the image renders. The Output format paragraph names the pair as a fourth case that keeps a real ledger, so "None - full markup was available" stays tied to markup arriving with the styles that resolve its values.

## [1.4.0] - 2026-09-12

- A report covering more than one screen had no legal shape. The edge case asks for each screen under its own `##` subheading, which is the level the output format already gives to `## P0 - blocks use` and the ledger, so the screen headings and the severity headings landed at the same depth and nothing in the report marked where one screen's verdict ended.
- The accounting rule collided with it harder than the headings did. Every criterion lands in exactly one of the four homes, stated at report level, while a criterion can be a P0 on the first screen and clean on the second - two readings that one entry cannot hold. Whichever one got written, the other left the report, and a criterion that leaves the report reads as a pass.
- Accounting is now per audited screen. Each screen takes a `##` heading with its severity sections, its ledger and its suppressed roster at `###`, and carries a complete set of the four homes. The scope line moves under the screen heading, since it is the home for that screen's checked-and-clean criteria; the input-type line and the scope note stay at report level, one input and one method for the whole report.
- The ledger's expected length is stated as per screen too. A two-screen screenshot report holds two ledgers of about 13, not one shared between them, so the short-ledger symptom still works when a report covers more than one screen.
- The edge case used to open "Multiple screens or states in one screenshot", putting two cases with opposite handling under one heading. Several states of one screen are one screen with more evidence, and the extra state unlocks the partial criteria it covers under Step 3, so they are now separate bullets: one set of the four homes for the states case, one set per screen for the other.
- README: the accounting bullet says the count runs per screen.

## [1.3.0] - 2026-08-19

- A "quick check" or "just the big ones" request had no legal output. The edge case said to report P0 only, while the accounting rule says every criterion lands in exactly one of a severity finding, the scope line when checked and clean, or the not-verifiable ledger - and a criterion that produced a P1 finding withheld by the requested depth fits none of them. Dropping it is forbidden by name in the failure modes; putting it on the scope line states it came back clean, which is false; printing it disobeys the request.
- Added a fourth home, "Suppressed at this depth": one line per criterion whose finding the requested depth withholds, naming the SC number and the tier. Depth now limits what a finding says, never whether the report admits one exists.
- Brought the three statements of the accounting rule into agreement. Step 3 and the failure-modes list still named two homes, from before the three-home rule was added in 1.2.0, so a criterion that was checked and came back clean was "dropped" under one statement and correctly filed under another. Under the two-home wording the only way to satisfy them was to file a passing criterion in the not-verifiable ledger, which asserts the input could not reach it. That move is now ruled out explicitly.
- README: the accounting bullet lists all four homes, and a new FAQ answer covers asking for blockers only.

## [1.1.0] - 2026-08-06

- New edge case: a screenshot with an unknown scale. Target size (SC 2.5.8) is measured in CSS pixels, so a 2x or 3x screenshot measured in raw image pixels produces false findings in both directions. The audit now settles the scale first, or reports 2.5.8 as not verifiable.
